# Super Memory 架构图

## 一、四层架构总图

```
┌─────────────────────── ① 触发层（全部自动，无手动操作） ──────────────────────────┐
│                                                                                  │
│  A. 会话开始      B. 口令触发                C. launchd 定时（每 6 小时）          │
│     │               │                          │                                   │
│  AGENTS.md /       "记忆" "记住…"            digest.sh 调度器                     │
│  CLAUDE.md 全局     "消化积压" "recall"  →  有积压才起 worker（零积压零 token）    │
│  协议块注入         → 加载 SKILL.md            codex exec / opencode run /         │
│  （每个 harness 一份）                          kimi -p / claude -p（headless）     │
└──────────────────────────────────────────────────────────────────────────────────┘
      │ 召回（协议一）                              │ 蒸馏（协议二）
      ▼                                            ▼
┌───────────────── ② LLM 判断层（只做判断，不碰存储） ─────────────────────────────┐
│                                                                                 │
│   读浓缩转录 + 既有 index ──► 判断"什么值得长期记" ──► 产出 ops JSON              │
│                                                                                  │
│   ops = [ { action: create|append|revise,   ← 一个事实一个页面，去重合并           │
│             page: "mcp-gateway",            ← 写入时"编译"，非检索时拼凑           │
│             section, content, links: [...] } ← 页面互链，每条事实带来源标签 ]       │
└──────────────────────────────┬──────────────────────────────────────────────────┘
                               │ ops JSON + checkpoint（确认契约）
                               ▼
┌────────────── ③ CLI 确定性层（零依赖 Python 标准库，无 LLM、无向量库） ────────────┐
│                                                                                 │
│   蒸馏方向（写）                     召回方向（读）                                │
│   ───────────────                    ───────────────                              │
│   pending --json                     inject "关键词" "改写" --max-chars 4000    │
│     增量解析日志→浓缩转录              search "关键词" -n 5                        │
│     （≤12000 字符+checkpoint）        打分：slug/标题+5 summary+3 正文+1×次数      │
│   apply --ops --checkpoint           分词：英文词元/中文bigram/弱词干               │
│     校验 schema→落盘→推游标           top5 页渲染成 markdown 记忆块                  │
│   ingest（备选：走 OpenAI 兼容 API 无人值守）                                      │
│   status                            （蒸馏 worker 会话被解析器按 prompt 前缀跳过， │
│                                      防自噬：蒸馏器不会蒸馏自己）                  │
└──────┬──────────────────────────────────────────────┬───────────────────────────┘
       │ 读（增量游标）                                │ 读写（纯 markdown）
       ▼                                             ▼
┌──── ④ 数据层 ────────────────────────────┐  ┌── 存储层 ~/.super-memory/ ─────────┐
│ harness 原始会话（私有格式，各一套 parser） │  │ wiki/pages/<slug>.md   知识页面    │
│                                          │  │ wiki/index.md          全局索引    │
│ codex     sessions/*.jsonl     字节偏移   │  │                          （自动重建）│
│ opencode  opencode.db sqlite   时间戳游标  │  │ wiki/log.md            会话时间线  │
│ kimi      **/wire.jsonl        字节偏移   │  │ state.json             增量游标    │
│ claude    projects/**/*.jsonl  字节偏移   │  │ digest.log             定时任务日志 │
└──────────────────────────────────────────┘  └─────────────────────────────────────┘
```

**核心设计一句话**：LLM 只做「判断」（协议一构造改写查询、协议二产出 ops），CLI 包揽全部「确定性」（解析、校验、落盘、游标、检索）——两者职责严格分离。

## 二、记忆生命周期闭环（跨 harness 打通的地基）

```
   周一 codex 会话            周二 opencode 会话          周三 任意 harness 新会话
   讨论网关方案               踩了 Nginx 超时坑              "继续做网关方案"
        │                          │                          │
        ▼                          ▼                          ▼
   日志落盘 ~/.codex/         日志落盘 opencode.db        ① inject 召回（协议一）
        │                          │                     ←── 命中 wiki 页面
        └────────────┬─────────────┘                          │
                     ▼                                          │
        pending 解析增量（各自游标，互不干扰）                      │
                     │                                          │
                     ▼                                          │
        LLM 产出 ops ─────────────► apply 落盘 ─────────────► wiki（同一目录）
                     │                                          ▲
                     └─── 确认契约：只有列入 ops 的 session      │
                          才推进游标（不丢数据/可中断续跑）          │
                                                                 │
                     本周三会话日志 ──(下次 pending 时进入积压)─────┘  循环
```

## 三、开发仓库 → 运行时部署映射

```
   仓库（本目录）                          运行时（install.sh 渲染绝对路径后）
  ───────────────────────                ─────────────────────────────────────────
  src/super_memory/                      .venv/bin/supermemory        CLI 可执行
    ├─ cli.py                            ~/.super-memory/             记忆库+游标
    ├─ parser_{codex|opencode|kimi|claude}.py     （各 harness 日志 → 统一 Transcript）
    ├─ state.py / wiki.py / search.py
    ├─ distill.py                        （ingest 备选路径的 API 调用）
  codex/  SKILL.md + AGENTS.snippet.md   → ~/.codex/skills/super-memory/ + AGENTS.md
  opencode/ …                            → ~/.config/opencode/skills/… + AGENTS.md
  kimi/  …                               → ~/.kimi-code/skills/… + AGENTS.md
  claude/ …                              → ~/.claude/skills/… + CLAUDE.md
  scripts/digest_*.sh                    launchd: com.supermemory.digest（每 6h）
                                         worker = 各 harness headless CLI
```

新增 harness（比如 Trae）= 只加一组框住的文件：`parser_trae.py` + `trae/SKILL.md` + `digest_trae.sh`，其余层零改动——这是「harness 适配隔离」的设计意图。

## 三个理解关键点

1. **双向链路共用同一个 wiki**：左边写入（编译），右边读取（召回），中间的 wiki 是纯 markdown 中立格式——不绑定任何 harness，这是"记忆跟着人走"的实现基础
2. **没有 LLM 的模块图里全是确定性**：③ 层任何命令重跑都幂等（游标 + schema 校验 + 行级去重），出问题时每一环可以直接检查
3. **agent 是唯一租户**：蒸馏/召回都由各 harness 的 agent 自己执行，复用 harness 订阅——所以整个系统没有任何 API key、服务进程、向量库
